# Pi service isolation

The restricted CI transport needs two distinct privileges. Its deploy UID may query the root Tailscale LocalAPI for WhoIs and contact the public origin's loopback health endpoint. The private status socket stays root-only. An nftables UID rule controls IPv4 and IPv6 traffic. Unix socket access depends on filesystem permissions and the daemon's peer-credential checks.

## Preserve the trusted CI path

Inspect the effective tailscaled systemd unit, command line, group memberships, existing ACLs and local socket consumers. The supplied drop-in targets a root Linux daemon with `RuntimeDirectory=tailscale` and `--socket=/run/tailscale/tailscaled.sock`. Confirm that `/var/run` resolves to `/run`. Check both primary and supplementary group memberships: only the transport account may belong to `portfolio-deploy`. Keep it out of privileged groups and Tailscale operator settings. Existing host users needing CLI access must use their authorized administrator path. [Tailscale service](https://github.com/tailscale/tailscale/blob/main/cmd/tailscaled/tailscaled.service) · [Linux socket permissions](https://github.com/tailscale/tailscale/blob/main/safesocket/unixsocket.go)

At an approved maintenance window with independent local recovery, install [the drop-in](tailscaled-whois.conf) root-owned in `/etc/systemd/system/tailscaled.service.d/portfolio-whois.conf`. The runtime directory starts root-only. The daemon's post-start hook grants the deploy group traversal of the known socket path. Confirm the effective directory is `root:portfolio-deploy 0710`, the socket is root-owned, and the deploy user can query WhoIs through the standard socket. This grants access to Tailscale's ordinary unprivileged LocalAPI methods. It does not make the deploy user an operator. Keep `/run/portfolio-dashboard` mode 0700 and its application socket mode 0600, both owned by root.

Check that the public web, tunnel, Caddy and dashboard UIDs all fail a connection to the standard LocalAPI socket, including outside their systemd namespaces. Confirm only root can connect to the dashboard socket. Verify a tagged CI release, rejection of the correctly keyed non-CI test peer, and existing human recovery access. Repeat after restart and reboot. Hold private ingress closed if these checks fail. To roll back this drop-in, disable private ingress first and restore the prior unit through the independent recovery session.

## Keep DNS working after host resolver changes

Install [stable-resolver.conf](stable-resolver.conf) as `90-stable-resolver.conf` in the service drop-in directories for `portfolio`, `portfolio-dashboard` and `cloudflared`. Append `BindReadOnlyPaths=/etc/portfolio-public/tunnel` to the **cloudflared copy only** for its scoped configuration and credential. The root-owned resolver source must contain the verified public upstreams allowed by the firewall. Each service gets a private read-only `/etc` with the resolver, trust store and listed runtime files. A host-side atomic replacement of `/etc/resolv.conf` can displace a file-only mount in a shared directory.

Validate the tunnel ingress configuration under the tunnel UID, reload systemd and restart the services individually. Compare each active process’s `/proc/<pid>/root/etc/resolv.conf` to the approved source. Verify a fresh SMTP TLS connection as the web UID, a new tunnel connection, the public homepage and both authenticated dashboard probes. Recheck these dependencies when adding features that need another file under `/etc`.

## Stage the packet filter

Use the actual Pi addresses, provider ranges and UIDs. Keep the inventory, generated rules and backups root-readable. For the initial private ts.net deployment, use the **status-only** stage. The [inventory example](host-guard.inventory.example.json) is inert. Copy it privately and replace the values for the chosen stage. The [renderer](render-host-guard.py) only reads JSON and writes an nft transaction to stdout. It can run offline. It leaves the live firewall untouched.

| Inventory field | Source |
| --- | --- |
| `local_prefixes` | All connected LAN prefixes (including global IPv6), protected routed subnets, VLANs and any extra JetKVM LAN addresses. Review actual routes and address assignments on the Pi. All stages also deny loopback, overlay and common nonpublic address space. |
| `resolver_addresses` | Exact nameserver IPs in the **effective service resolver configuration**. The migrated public units use a dedicated pre-Tailscale resolver file. Inspect `/etc/portfolio-public/public-resolv.conf` and account for both address families before rendering. Configure the private worker with the same approved public resolver view. Only DNS on TCP/UDP 53 is allowed to these addresses. |
| `jetkvm_ip`, `jetkvm_port` | Same single tailnet address and confirmed TCP port as the private worker. Needed in status-only and full pilot stages. |
| `public_egress_policy` | Choose `port-scoped` for rotating public transport and mail endpoints, or `provider-pinned` if an operator maintains their approved IP prefixes across changes. Only the former permits an arbitrary Internet host on the designated outbound port for each of those two UIDs. Both modes first deny protected routes and all other new destinations for the private workers. |
| `public_edge_prefixes`, `tunnel_edge_prefixes` | Reviewed public CDN endpoint ranges for the website check, and tunnel ranges when using `provider-pinned`. In `port-scoped` mode omit `tunnel_edge_prefixes`. Include all failover families for the configured region. The public website check uses TCP 443. Cloudflared uses QUIC on UDP 7844 or TCP 7844 for HTTP/2. [Cloudflare public ranges](https://www.cloudflare.com/ips/) · [Tunnel transport](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/) |
| `smtp_prefixes`, `smtp_port` | Supply the actual TLS submission port (465 or 587). Include reviewed relay/failover prefixes in `provider-pinned` mode and omit `smtp_prefixes` in `port-scoped` mode. Do not include the SMTP password in the inventory. |

1. **First-run guard.** Only `local_prefixes` and `resolver_addresses` are required. Render with `python3 render-host-guard.py first-run /path/to/private-inventory.json`. This stage confines the three deployed public UIDs and leaves input ports unchanged. It blocks their connections to tailnet, LAN and host-local destinations except approved DNS for public web/tunnel and HTTP 6050 for tunnel/deploy. Public web/tunnel internet egress remains available for existing SMTP and Cloudflare endpoints. The deploy UID has no other new IP egress. Keep private ingress disabled in this stage.
2. **Status-only guard for the first private pilot.** Render with `python3 render-host-guard.py status-only /path/to/private-inventory.json`. It needs only the three existing public UIDs and the new `portfolio-dashboard` UID. It guards private port 8443 on TCP and UDP off tailscale0. Existing non-pilot ingress is unaffected. The worker can use its exact upstream DNS addresses, the fixed website's public edge on TCP 443, and one JetKVM endpoint over tailscale0. All four UIDs otherwise have default-denied new egress except public SMTP, tunnel transport and deploy/tunnel HTTP 6050. Choose `port-scoped` for rotating public SMTP/tunnel addresses. The Unix-socket restrictions above and the tailnet grant/device checks still apply. No ACME origin, apex proxy or split DNS is needed for this stage.
3. **Full apex pilot guard.** Provision the additional service accounts and finish the inventory, then render with `python3 render-host-guard.py pilot /path/to/private-inventory.json`. All six service UIDs have default-denied new egress. The locked `portfolio-dns` UID may send DNS requests only to the listed upstreams. The example reserves TCP/UDP port 53 on the Pi exclusively for tailnet ingress; check for existing LAN DNS servers and loopback stubs before applying it. Use real upstreams for service resolution, and match the CoreDNS upstream file to the inventory. The only permitted application connection through tailscale0 is the status worker's exact JetKVM IP and port. The loopback HTTP-01 origin must itself bind only to 127.0.0.1:83. Check for other host users of the guarded ingress ports, including LAN HTTPS and HTTP/3, before applying the pilot stage. Grant the intended resolver clients TCP and UDP 53 in the tailnet policy. Enforce tailnet grants independently for Serve, even if traffic to its userspace listener is absent from host nft counters.
4. **Before applying a stage.** Save the active rules, inspect existing input/output priorities and ensure each named UID exists and is exclusive. Render to a fresh private file, inspect it, and run `nft --check --file <rendered-file>` on the target kernel. A failed render or check stops the change. All stages replace only the table `inet portfolio_private_guard` in a single batch. Confirm that name belongs to this deployment. Prepare a rollback that restores only this table from its prior contents, or deletes just this table for a first install. Arrange independent console/timed rollback before the approved change. Preserve the system and Tailscale rule sets. [nftables command reference](https://netfilter.org/projects/nftables/manpage.html)
5. **Verify under the real service identities.** Check DNS over the effective resolvers, tunnel reconnect, public homepage and custom 403, approved SMTP delivery or separately authorized relay connectivity, CI deploy health and WhoIs, and, for the full apex pilot, the HTTP-01 path with a synthetic token. Check the KVM's tailnet and LAN addresses are denied to each public UID, in IPv4 and IPv6. For either private stage, verify the status worker’s only application destinations are the KVM tailnet TCP port and fixed public health endpoint, the tunnel cannot reach private status, and public visitors can still use the site. For the full apex stage, verify Caddy can reach only its public backend. Test fresh connections as well as existing ones.
6. **Persist the verified stage.** Integrate the reviewed table with the existing host firewall boot mechanism and ensure it loads before private listeners. Verify the boot order and outcomes after reboot with recovery access. Retain the provider-pinned inventory and revisit it before address changes, or use port-scoped public egress where maintenance cannot track SMTP and tunnel rotations. Track public-site CDN ranges, LAN prefix and upstream resolver changes in each private stage. Render, review, check and replace the table atomically. A renderer never adds addresses discovered through an unverified DNS response. Close private ingress before reverting from pilot to first-run rules.
