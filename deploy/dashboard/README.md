# One-Pi dashboard gateway

These templates target a systemd Linux Pi running the public Rust server, its Cloudflare tunnel, one root-owned Tailscale daemon, Caddy and a separately installed read-only status binary. The public deployment pipeline has no need for a tailnet login to the dashboard, access to its files or permission to install units. Host root and the kernel remain shared trust boundaries. Keep privileged operations outside this pilot.

| Traffic | Listener | Destination |
| --- | --- | --- |
| Public apex | Existing Cloudflare hostname and tunnel | Public app on `127.0.0.1:6050`, including its custom 403 |
| Approved device visiting the apex | Caddy on the Pi tailnet address, TCP 443 | Static dashboard landing or the fixed public app |
| Sandboxed status frame or direct private view | Native Tailscale Serve at the Pi’s MagicDNS HTTPS name, TCP 8443 | Root-owned Unix socket. App checks Serve's user login for every route |
| Interactive shell | Tailscale SSH Console initiated on the Machines page | Tailscale SSH check rule, human operator and one restricted Pi account |

## Prepare for an approved installation

1. Record the Pi's current root-owned units, public tunnel ingress, service accounts, sudoers, SSH access, DNS and effective tailnet policy. Preserve a working local recovery session. Complete the public deployment isolation migration first. Verify public CI can install only public artifacts through its restricted key/forced-command path. Check public runtime, deploy and tunnel identities have no general sudo, operator privileges, privileged groups, writable unit or executable paths, SSH forwarding or access to private files. Keep public SMTP credentials accessible only to the public runtime and the tunnel-scoped token accessible only to its dedicated tunnel process. The runtime connector has no need for an account-wide Cloudflare certificate.
2. Tailnet grants identify the Pi, so every process on it would otherwise inherit the same network reach. Reserve distinct Linux accounts for Caddy, the public runtime, deploy, tunnel and status service. The restricted CI helper uses the local Tailscale socket to verify the runner’s identity. Reserve a dedicated group containing only the deploy UID for directory traversal. Where tailscaled uses a root-owned systemd runtime directory, use a reviewed startup hook to set its group and mode 0710 after creation, before serving requests. Verify the socket permissions permit an unprivileged WhoIs query from the deploy UID. Keep Tailscale operator privileges with the administrator. Keep Caddy, the status worker, the public app and the tunnel out of the traversal group. Confirm their UIDs cannot open the socket, and verify both a tagged CI release and rejection of a correctly keyed non-CI peer after a daemon restart and reboot. Keep the status backend’s separate Unix socket accessible only to root and tailscaled. Apply equivalent isolation to any alternate socket, local proxy, container engine or operator mechanism. Review local consumers before changing access.
3. Stage the firewall first. `private-guard.nft.example` supplements the Pi's existing default-deny host firewall. Populate the exact approved JetKVM tailnet address and TCP port, public DNS resolver/stub and provider endpoint sets. The example is IPv4 for JetKVM and DNS. For IPv6 substitute the corresponding nftables address family and exact address. Keep overlay, LAN and loopback addresses outside the provider sets. Resolve public names through a trusted resolver, select the currently used SMTP port and restrict records to verified provider ranges. Stage updated endpoint sets atomically when providers change. Review the Pi's existing input/forward policies for both families, including container/NAT and services listening on LAN. Limit DNS TCP and UDP 53 to the resolver's intended clients and interface. Reserve public web ingress to the outbound tunnel. Review for dependencies on other services before using the example's port guards. Validate with `nft --check --file <prepared-file>` after creating the referenced accounts. Start with local console recovery, then verify SMTP, Cloudflare tunnel reconnect and the public health URL before accepting the change. [Cloudflare Tunnel firewall](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/) · [Cloudflare web proxy ranges](https://www.cloudflare.com/ips/)
4. Produce a private, reviewed copy of `tailnet-policy.hujson.example` with the owner's confirmed identities and ports. Retain the Pi's existing service tag as needed and add the Pi-specific tag only to this Pi. The KVM host alias is one confirmed node IP, so the user-owned KVM can retain its existing identity. Keep all tag owners and the CI OIDC trust narrow. Merge with the **whole** policy and examine existing grants, ACLs, node shares, SSH rules and node attributes. Remove overlapping allows, including any broad default allow, and remove Funnel capability and configuration from the gateway. Run both positive and negative policy tests against the combined result. Add the specific grant for DNS clients to TCP/UDP 53 if the Pi runs the split resolver. When the lookup must return public answers to non-viewers, those clients need DNS reachability too. DNS access conveys no HTTPS access. The viewer grant selects individual enrolled workstation addresses. Use the same approved v4/v6 peer set for Caddy and the private DNS view. Exclude the KVM even if it belongs to the viewer’s account. Serve’s app allowlist separately requires the approved human login. If posture is available, a verified managed-device condition scoped to a human group can replace manual workstation selectors. Restrict SSH access separately. [Tailscale grants](https://tailscale.com/docs/reference/syntax/grants) · [Tailscale identity](https://tailscale.com/docs/concepts/tailscale-identity)
5. Use the DNS view in `Corefile.example` or the equivalent in the deployed resolver. Keep public apex records, other record types and unrelated subdomains intact. For the private view, supply only working tailnet addresses and suppress incompatible public AAAA, HTTPS and SVCB hints. Grant split DNS clients direct access to this resolver so its per-client view can distinguish them. Keep the source IP list synchronized with device approval/revocation. Authorization remains in grants and the status service. Configure the Pi itself to retain a public DNS view for its outbound HTTPS health check (for example, an approved `tailscale set --accept-dns=false` on the Pi). Use an independently configured public upstream in the private DNS server to avoid a forwarding loop. Check managed browser DNS, exit nodes, IPv6, network changes, connection reuse and cache expiry on actual clients. A packet denied by grants never reaches HTTP. Giving a connected non-viewer the public DNS view preserves both the portfolio and its 403. [Tailscale split DNS](https://tailscale.com/docs/reference/dns-in-tailscale)
6. Provision a **separate apex TLS key pair** for Caddy using DNS-01 and a root-controlled renewal process. Prefer delegation of `_acme-challenge` to a validation-specific zone or assign tightly scoped credentials to a separate issuer. Check the public provider's existing certificate validation records, CAA and renewal flow before adding a delegation. Install the full chain and key atomically at the exact Caddyfile paths with ownership `root:caddy`, private key mode `0640`, directory mode `0750`. Caddy has no DNS API token or Cloudflare tunnel credential. Validate the new pair, restart Caddy to load it (the admin API is disabled), check expiry and alert on renewal failure. Wildcards, public ingress and port 80 are unnecessary for this certificate. [Let’s Encrypt DNS-01](https://letsencrypt.org/docs/challenge-types/) · [Caddy HTTPS](https://caddyserver.com/docs/automatic-https)
7. Enable MagicDNS and Tailscale HTTPS for the private Serve hostname through the approved settings. Its DNS name appears in public certificate transparency logs. Use a neutral machine name if this disclosure matters. In *private installed copies* of the Caddyfile and landing HTML replace `status.example.invalid` with the verified full MagicDNS hostname, without a scheme, slash or port. The fixed target remains TCP 8443. Replace the documentation viewer addresses in Caddy's direct-peer matcher with the approved workstations. Replace both documentation bind addresses with the Pi's actual `tailscale0` addresses, or omit an unsupported address family together with its private DNS record. Check for an existing 443/8443 listener. Install the Caddyfile and landing HTML as root-owned, non-writable by the runtime UIDs. Install only `landing.html` under `/usr/local/share/portfolio-dashboard`. Validate with `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`. Use the packaged non-root Caddy unit, ensure tailscale0 is ready before Caddy starts, disable restart loops until prerequisites work, and mask access to dashboard/Tailscale control sockets in that unit. [Caddy binding](https://caddyserver.com/docs/caddyfile/directives/bind) · [Tailscale certificates](https://tailscale.com/docs/how-to/set-up-https-certificates)
8. Build the independent Rust service for the Pi's verified architecture. Through an operator-controlled installation, place it at `/usr/local/libexec/portfolio-dashboard`, root-owned and executable. Create the locked `portfolio-dashboard` system account and group with no home or login. Place the supplied systemd service and socket in the system unit directory. Create root-only `/etc/portfolio-dashboard/status.env` (mode `0600`, parent `0700`), containing `DASHBOARD_VIEWERS` (comma-separated exact human Tailscale logins), `DASHBOARD_JETKVM_IP` (one verified tailnet IP) and `DASHBOARD_JETKVM_PORT` (one verified listening port). Treat viewer list changes as reviewed configuration changes. Use the separate resolver-readable /etc/portfolio-dns/public-resolv.conf for CoreDNS. The optional DASHBOARD_PI_MACHINE is only a display hint in the authenticated Machines console instructions. See status.env.example. Validate with `systemd-analyze verify`. Enable the **socket** unit. Its parent and socket are owned by root. Systemd passes the already-open descriptor to the unprivileged backend. Verify modes after restart and keep the parent unwritable by the service.
9. On the planned Linux installation, check `tailscale serve --help` for Unix-domain socket support. With the grants, firewall and socket in place, the planned root operation is `tailscale serve --bg --https=8443 unix:/run/portfolio-dashboard/app.sock`. Inspect `tailscale serve status` and `tailscale funnel status` for the expected private route only. Only root/tailscaled can open the socket. The HTTP proxy removes client-supplied Tailscale identity headers and supplies the identity associated with the peer. A tagged machine or unlisted shared user cannot satisfy the service's human viewer allowlist. Keep Serve on TCP 8443 so Caddy owns the apex TCP 443 listener. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) · [Unix socket support in v1.104.6](https://github.com/tailscale/tailscale/blob/v1.104.6/cmd/tailscale/cli/serve_v2.go)

## Routing and isolation

The apex contains a script-free, cookie-free landing document. Its iframe displays only two read-only status values on the separate HTTPS origin. An empty sandbox removes script, forms and top navigation, the parent CSP fixes the iframe origin, and the private embed limits permitted ancestors. A compromised public site can present a misleading shell or cover the frame. A permitted workstation whose app login fails can still receive HTTP 200 for this landing while Serve returns a 403 for its frame. A stale/misrouted peer that reaches Caddy but misses the workstation matcher receives the public 403. Keep all sensitive detail and operator actions top-level on an independently verified origin. A stricter top-level-only design removes the iframe, changes the parent's `frame-src` to `'none'`, and disables the embed endpoint. Keep the two top-level links. If the landing stylesheet changes, update its CSP hash.

Caddy uses exactly one public upstream, the Pi's loopback public app. The reverse proxy reconstructs public request headers and drops response cookies and alternate-service hints. Only the contact POST receives the direct TCP peer in `CF-Connecting-IP`, after any submitted forwarding fields have been discarded. This preserves the existing loopback trust configuration and per-peer contact rate limit. Other local processes allowed to call the public origin directly could influence this public limiter, so restrict local reachability. The public Rust app and its tunnel never receive a private status response. Configure the tunnel with exact public hostname and loopback origin, a terminal 404 for unmatched hosts, and no routes to the gateway, Serve or DNS. Configure a Cloudflare cache bypass for the exact dashboard path and its subtree before any cache-everything rule. Purge earlier dashboard objects and review public Workers and service-worker registrations on the apex.

The status worker can make a TCP connection to one JetKVM port and fetch the public website's fixed HTTPS health response. Enforce both the host process egress policy and node grants. A compromised status worker still has TCP access to that one KVM port. Require independent JetKVM authentication, and prefer an unprivileged health listener if the device supports one. Reserve remote input, KVM credentials, arbitrary commands, service restarts and terminal access for independent operator flows.

The private dashboard links to the official Tailscale Machines page. An eligible operator selects the Pi and starts SSH to its restricted OS account. The Console currently requires an Owner, Admin, IT admin or Network admin and creates an ephemeral browser node. Tailscale SSH must already be enabled on the Pi and both the port grant and SSH check rule must authorize the human. Existing MFA/IdP configuration must actually enforce strong reauthentication. Keep the dashboard viewer and operator roles distinct. The example narrows the shell grant to the Console’s JavaScript node posture. Check the actual ephemeral node’s attributes, retain independent recovery access, and run the supplied SSH tests against every overlapping rule. For native recovery SSH, pair a TCP 22 network grant from each approved workstation’s enrolled IPv4 and IPv6 addresses with an SSH check rule for the named human and exact local account. Successful sessions can send replies without a reverse grant. Add same-family policy tests that allow each workstation to reach the Pi on TCP 22 and deny the Pi access to each workstation on TCP 22. These rules govern tailnet paths. Ordinary key-based deployment uses its separate tailnet-bound OpenSSH listener on 2222 and a restricted account/key. [Tailscale SSH Console](https://tailscale.com/docs/features/tailscale-ssh/tailscale-ssh-console) · [Tailscale SSH check mode](https://tailscale.com/docs/features/tailscale-ssh)

## Pre-release and rollback

On an approved staging instance, inspect both IP families, actual Tailscale state and active sockets. Verify the authorized browser sees both status rows under the apex, a direct private view, and a separate SSH Console flow. Check iframe layout and fallback in each supported browser, especially with local-network privacy controls. Verify the public page, resume, social redirects, public contact validation and duplicate limits from both network views. Exercise a non-viewer, a tagged node, a stale DNS client, a disconnected browser, a direct origin and the tunnel's catch-all. Check denied responses and cache headers, wrong Host/SNI, direct/private listener isolation and identity header handling. Confirm the public runtime, CI and tunnel UIDs cannot open the Unix socket, fetch status or reach the KVM, even from the Pi. Verify that the app loses its KVM reach when the grant is removed and that stale viewers fail a fresh request. Verify the same outcomes after reboot, after certificate renewal and after Web/SSH/Tailscale restarts. Preserve results privately.

For an approved rollback, return split DNS clients to the public answer, remove only the dedicated Serve 8443 handler, stop the private Caddy listener and status socket/service, and revoke the new dashboard-specific permissions. Let short DNS TTLs expire and retest with the Pi's independent management path. Keep the public 403, the public tunnel and the public deployment isolation. The sandboxed iframe and overlay status are display conveniences. Loss of the gateway, nameserver or Tailscale can interrupt the private view.
