# One-Pi dashboard gateway

These templates target a systemd Linux Pi running the public Rust server, its Cloudflare tunnel, one root-owned Tailscale daemon, Caddy and a separately installed read-only status binary. The public deployment pipeline has no need for a tailnet login to the dashboard, access to its files or permission to install units. Host root and the kernel remain shared trust boundaries. Keep privileged operations outside this pilot.

| Traffic | Listener | Destination |
| --- | --- | --- |
| Public apex | Existing Cloudflare hostname and tunnel | Public app on `127.0.0.1:6050`, including its custom 403 |
| Approved device visiting the apex | Caddy on the Pi tailnet address, TCP 443 | Static dashboard landing or the fixed public app |
| Sandboxed status and inbox frames or direct private view | Native Tailscale Serve at the Pi’s MagicDNS HTTPS name, TCP 8443 | Root-owned Unix socket. App checks Serve's user login for every route |
| Interactive shell | Native SSH from an approved operator computer | Tailscale SSH identity check and the configured local Pi account |

## Test the private URL first

For the independent status pilot, use the Pi’s MagicDNS name on HTTPS port 8443. Keep the existing public 403 at the apex. This phase uses Tailscale Serve, the dashboard systemd units and the `status-only` host firewall. It needs no Caddy, CoreDNS, public certificate validation route or split DNS changes. Confirm MagicDNS and Tailscale HTTPS are enabled. Issuing a certificate discloses the Pi’s MagicDNS hostname in public certificate transparency logs.

Install the reviewed ARM64 artifact and the host-local status configuration, then follow the [host isolation procedure](host-isolation.md). Install the rendered rules at `/etc/portfolio-dashboard/guard.nft` and install `portfolio-dashboard-guard.service` beside the dashboard socket and service units. The socket requires the kernel to accept the rules before the app can receive requests. The worker uses the existing public deployment’s resolver file so its website health check goes through the public origin. Check both the website and KVM readings from an approved device. The separate native SSH session requires its own authorization on an operator computer. To withdraw the pilot, remove only the Serve handler on port 8443, stop the dashboard socket and service, and preserve the public deployment controls.

## Prepare for an approved installation

1. Record the Pi's current root-owned units, public tunnel ingress, service accounts, sudoers, SSH access, DNS and effective tailnet policy. Preserve a working local recovery session. Complete the public deployment isolation migration first. Verify public CI can install only public artifacts through its restricted key/forced-command path. Check public runtime, deploy and tunnel identities have no general sudo, operator privileges, privileged groups, writable unit or executable paths, SSH forwarding or access to private files. Keep public SMTP credentials accessible only to the public runtime and the tunnel-scoped token accessible only to its dedicated tunnel process. The runtime connector has no need for an account-wide Cloudflare certificate.
2. Isolate the root Tailscale LocalAPI socket using the [host isolation runbook](host-isolation.md). The existing restricted deploy account needs unprivileged WhoIs to verify CI. The supplied tailscaled drop-in grants only its dedicated group directory traversal after daemon startup. Keep the separate private backend socket root-only. Verify both a tagged CI release and rejection of a correctly keyed non-CI peer after a daemon restart and reboot.
3. Prepare a host-local firewall inventory from the actual public-service resolver, LAN prefixes, JetKVM endpoint, SMTP relay and tunnel/CDN ranges. The [host isolation runbook](host-isolation.md) covers rendering the four-UID status-only guard for the private ts.net pilot, the separate full-apex guard, service-UID checks and rollback. Keep private ingress closed until the pilot guard and effective grants both pass their checks.
4. Produce a private, reviewed copy of `tailnet-policy.hujson.example` with the owner's confirmed identities and ports. Retain the Pi's existing service tag as needed and add the Pi-specific tag only to this Pi. The KVM host alias is one confirmed node IP, so the user-owned KVM can retain its existing identity. Keep all tag owners and the CI OIDC trust narrow. Merge with the **whole** policy and examine existing grants, ACLs, node shares, SSH rules and node attributes. Remove overlapping allows, including any broad default allow, and remove Funnel capability and configuration from the gateway. Run both positive and negative policy tests against the combined result. Add the specific grant for DNS clients to TCP/UDP 53 if the Pi runs the split resolver. When the lookup must return public answers to non-viewers, those clients need DNS reachability too. DNS access conveys no HTTPS access. The viewer grant selects individual enrolled workstation addresses. Use the same approved v4/v6 peer set for Caddy and the private DNS view. Exclude the KVM even if it belongs to the viewer’s account. Serve’s app allowlist separately requires the approved human login. If posture is available, a verified managed-device condition scoped to a human group can replace manual workstation selectors. Restrict SSH access separately. [Tailscale grants](https://tailscale.com/docs/reference/syntax/grants) · [Tailscale identity](https://tailscale.com/docs/concepts/tailscale-identity)
5. Use the DNS view in `Corefile.example` or the equivalent in the deployed resolver. Keep public apex records, other record types and unrelated subdomains intact. For the private view, supply only working tailnet addresses and suppress incompatible public AAAA, HTTPS and SVCB hints. Grant split DNS clients direct access to this resolver so its per-client view can distinguish them. Keep the source IP list synchronized with device approval/revocation. Authorization remains in grants and the status service. The Pi is outside the viewer set and may query its own resolver over loopback. The status worker uses its isolated public resolver for the website health probe. Use an independently configured public upstream in the private DNS server to avoid a forwarding loop. Check managed browser DNS, exit nodes, IPv6, network changes, connection reuse and cache expiry on actual clients. A packet denied by grants never reaches HTTP. Giving a connected non-viewer the public DNS view preserves both the portfolio and its 403. [Tailscale split DNS](https://tailscale.com/docs/reference/dns-in-tailscale)
6. Provision a browser-trusted apex certificate for Caddy. The installed HTTP-01 approach uses the existing public tunnel for a single token path, a privileged loopback responder, a root-only Certbot lineage and an atomic deployment hook. The gateway service must be installed and inactive before first issuance. Follow the [HTTP-01 issuance and renewal procedure](acme-http-01.md). An independently managed DNS-01 issuer is also suitable if the operator already has a delegated challenge zone. Keep DNS credentials outside the web services.
7. Enable MagicDNS and Tailscale HTTPS for the private Serve hostname through the approved settings. Its DNS name appears in public certificate transparency logs. Use a neutral machine name if this disclosure matters. In *private installed copies* of the Caddyfile, landing HTML and messages HTML replace `status.example.invalid` with the verified full MagicDNS hostname, without a scheme, slash or port. In the installed landing HTML also replace PI_SSH_USER with the approved non-root Pi account. The status frame uses TCP 8443. Replace the documentation viewer addresses in Caddy's direct-peer matcher with the approved workstations. Replace both documentation bind addresses with the Pi's actual `tailscale0` addresses, or omit an unsupported address family together with its private DNS record. Check for an existing 443/8443 listener. Install the Caddyfile and landing HTML as root-owned, non-writable by the runtime UIDs. Install `landing.html` and `messages.html` under `/usr/local/share/portfolio-dashboard`. Validate with `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`. Install the supplied portfolio-gateway.service and portfolio-dns.service under /etc/systemd/system. Install the verified Caddy and CoreDNS executables under /usr/local/libexec as portfolio-caddy and portfolio-coredns. The units require the full firewall stage and the tailscale0 device. Test a private address override and direct DNS over TCP and UDP, then enable both units and add the Pi as a Tailscale restricted nameserver for treymouledoux.me. Keep exit-node and global resolver settings at their existing values unless separately approved. [Caddy binding](https://caddyserver.com/docs/caddyfile/directives/bind) · [Tailscale certificates](https://tailscale.com/docs/how-to/set-up-https-certificates)
8. Build the independent Rust service for the Pi's verified architecture. Through an operator-controlled installation, place it at `/usr/local/libexec/portfolio-dashboard`, root-owned and executable. Create the locked `portfolio-dashboard` system account and group with no home or login. Place the supplied systemd service and socket in the system unit directory. Create root-only `/etc/portfolio-dashboard/status.env` (mode `0600`, parent `0700`), containing `DASHBOARD_VIEWERS` (comma-separated exact human Tailscale logins), `DASHBOARD_JETKVM_IP` (one verified tailnet IP) and `DASHBOARD_JETKVM_PORT` (one verified listening port). Treat viewer list changes as reviewed configuration changes. Use the separate resolver-readable /etc/portfolio-dns/public-resolv.conf for CoreDNS. Configure the optional DASHBOARD_PI_MACHINE and DASHBOARD_PI_SSH_USER for the native SSH instructions. See status.env.example. Validate with `systemd-analyze verify`. Enable the **socket** unit. Its parent and socket are owned by root. Systemd passes the already-open descriptor to the unprivileged backend. Verify modes after restart and keep the parent unwritable by the service.
9. On the planned Linux installation, check `tailscale serve --help` for Unix-domain socket support. With the grants, firewall and socket in place, the planned root operation is `tailscale serve --bg --https=8443 unix:/run/portfolio-dashboard/app.sock`. Inspect `tailscale serve status` and `tailscale funnel status` for the expected private route only. Only root/tailscaled can open the socket. The HTTP proxy removes client-supplied Tailscale identity headers and supplies the identity associated with the peer. A tagged machine or unlisted shared user cannot satisfy the service's human viewer allowlist. Keep Serve on TCP 8443 so Caddy owns the apex TCP 443 listener. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) · [Unix socket support in v1.104.6](https://github.com/tailscale/tailscale/blob/v1.104.6/cmd/tailscale/cli/serve_v2.go)

## Routing and isolation

Authorized devices open the dashboard at `/dashboard` and its inbox at `/dashboard/messages`. Caddy serves only the two static wrappers. Each embeds a fixed document from the separate Serve origin. The inbox requires an explicitly authorized reader as well as dashboard viewer access. The apex receives no message data, cookies or private API credentials. Follow the [contact inbox storage procedure](inbox-storage.md) to grant the service read-only access to the local message file and configure `DASHBOARD_INBOX_READERS` for the intended human. Keep contact submissions out of static files, public assets and CDN caches. If either wrapper stylesheet changes, update its CSP hash.

The frames are read-only. Their sandbox disables scripts, forms and top navigation, and their CSP limits embedding to the exact portfolio origin. A compromised public portfolio could still imitate the dashboard or overlay a real frame on an authorized device. The inbox can open a dedicated confirmation tab at the private Serve origin. An inbox administrator verifies a passkey on that origin and arms the selected operation. Completing the five-second hold submits the target-specific approval. The confirmation page denies framing. Native SSH runs on an independently authorized computer. A private wrapper can return HTTP 200 while its frame denies the human identity. Devices routed to the public site receive the custom 403.

Caddy uses exactly one public upstream, the Pi's loopback public app. The reverse proxy reconstructs public request headers and drops response cookies and alternate-service hints. Only the contact POST receives the direct TCP peer in `CF-Connecting-IP`, after any submitted forwarding fields have been discarded. This preserves the existing loopback trust configuration and per-peer contact rate limit. Other local processes allowed to call the public origin directly could influence this public limiter, so restrict local reachability. The public Rust app and its tunnel never receive a private status response. The tunnel uses the exact public hostname and loopback portfolio origin, with a terminal 404 for unmatched hosts. The scoped ACME token rule precedes the portfolio rule. Private responses come directly from Caddy and Serve. Configure a Cloudflare cache bypass for the exact dashboard path and its subtree before any cache-everything rule. Purge earlier dashboard objects and review public Workers and service-worker registrations on the apex.

The status worker can make a TCP connection to one JetKVM port and fetch the public website's fixed HTTPS health response. Enforce both the host process egress policy and node grants. A compromised status worker still has TCP access to that one KVM port. Require independent JetKVM authentication, and prefer an unprivileged health listener if the device supports one. Reserve remote input, KVM credentials, arbitrary commands, service restarts and terminal access for independent operator flows.

The private dashboard displays the native SSH command for the configured Pi. Operators run it on an approved computer. Pair a TCP 22 grant from each operator computer’s enrolled IPv4 and IPv6 addresses with a Tailscale SSH check rule for the named human and exact local account. Keep the viewer list independent of the operator devices. A viewer can see the command without gaining shell access. Successful sessions can send replies without a reverse grant. Add same-family tests that allow the computers to reach the Pi on TCP 22 and deny the Pi access to those computers on the same port. These rules cover tailnet paths. Public CI uses a separate OpenSSH listener on TCP 2222 with its own key and forced command. [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)

## Pre-release and rollback

On an approved staging instance, inspect both IP families, actual Tailscale state and active sockets. Verify the authorized browser sees both status rows under the apex, a direct private view, and a separate native SSH login. Check iframe layout and fallback in each supported browser, especially with local-network privacy controls. Verify the public page, resume, social redirects, public contact validation and duplicate limits from both network views. Exercise a non-viewer, a tagged node, a stale DNS client, a disconnected browser, a direct origin and the tunnel's catch-all. Check denied responses and cache headers, wrong Host/SNI, direct/private listener isolation and identity header handling. Confirm the public runtime, CI and tunnel UIDs cannot open the Unix socket, fetch status or reach the KVM, even from the Pi. Verify that the app loses its KVM reach when the grant is removed and that stale viewers fail a fresh request. Verify the same outcomes after reboot, after certificate renewal and after Web/SSH/Tailscale restarts. Preserve results privately.

For an approved rollback, return split DNS clients to the public answer, remove only the dedicated Serve 8443 handler, stop the private Caddy listener and status socket/service, and revoke the new dashboard-specific permissions. Let short DNS TTLs expire and retest with the Pi's independent management path. Keep the public 403, the public tunnel and the public deployment isolation. The sandboxed iframe and overlay status are display conveniences. Loss of the gateway, nameserver or Tailscale can interrupt the private view.
