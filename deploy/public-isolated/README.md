# Isolate the public deployment on a shared Pi

This is an opt-in migration for the existing locally managed public Cloudflare Tunnel. Schedule a short maintenance window and obtain approval before applying it. Confirm the Pi's distribution, Python 3.9+, cgroup/BPF support, DNS resolver, SMTP delivery, current tunnel mappings, firewall and an independent administrator recovery login. The public release job runs only on main with the repository variable PORTFOLIO_DEPLOY_MODE set to isolated. Removing the variable pauses releases. CI sends only the public binary and assets through the dedicated listener. Complete the migration **before** putting a private dashboard on the same machine.

## Provision once as the host administrator

1. Create three distinct local UIDs with their own groups: `portfolio-public` (HTTP service), `portfolio-tunnel` (public tunnel) and `portfolio-deploy` (CI transport). Give the services nologin shells. Give the deploy UID a root-owned empty home and no writable login files. Install the supplied `deploy-shell` root-owned, mode 0755, as `/usr/local/libexec/portfolio-deploy-shell` and set this exact path as the deploy account’s login shell. It accepts only OpenSSH’s fixed activation command. Keep the Debian account enabled, unexpired and password-locked. The dedicated sshd explicitly enables PAM account/session processing and disables both password entry methods. Verify the local PAM account rules allow public-key sessions for this locked-password UID, including any local shell allowlist. Configure public-key-only authentication for this account on the dedicated listener. Deny the deploy account on other SSH listeners and in Tailscale SSH policy. Limit human Pi SSH rules to explicitly named human accounts. Keep all three UIDs out of privileged groups, including sudo, docker, disk, systemd-journal and Tailscale operator access.
2. As root, install the reviewed `activate.py` as `/usr/local/libexec/portfolio-public-activate` mode 0755. Install `sudoers.example` as a root-owned mode 0440 sudoers fragment after validating with `visudo -cf`. Check the complete effective permission list with `sudo -l -U portfolio-deploy`. The only permitted root command is the literal `/usr/bin/systemctl restart portfolio.service`. The unit, all drop-ins, system binaries and their parent directories must be root-owned and immutable to those three UIDs.
3. Create `/srv/portfolio` root-owned. Create `/srv/portfolio/public` and its `releases` directory owned by `portfolio-deploy:portfolio-public` mode 0750. The runtime group needs traversal and read access. Seed a reviewed, known-good public binary and its matching assets under `releases/0-1/`, including the public 403 implementation. Use 0555 for the binary, 0444 for files and 0755 for directories. Create the **relative** symlink `/srv/portfolio/public/current -> releases/0-1`. CI publishes only the public binary and static assets here. All switch operations must stay on one filesystem. Allocate a release-space quota or separate filesystem and monitor capacity. Keep the current release, any target in `.rollback-target` and at least one known-good predecessor when pruning inactive releases during a locked maintenance window.
4. Stage the supplied root-owned service units under `/etc/systemd/system/`. `portfolio.service` binds only `127.0.0.1:6050`. Root supplies the application-specific SMTP credential via `LoadCredential=portfolio-contact-smtp.json`; confirm the existing credential store or configure an absolute root-readable source. The web process can read this credential and its own submissions. It also reads the editable recipient list at `/etc/portfolio-contact/recipients.json`, so install `contact-recipients.conf` as `96-contact-recipients.conf` in the same drop-in directory: the private read-only `/etc` supplied by `90-stable-resolver.conf` hides every path it does not name, and without that bind the site silently falls back to the credential's single address. Use a send-only restricted SMTP account, narrow relay, sender/recipient rules and rate limits. Keep DNS/API tokens, Pi login credentials and tunnel credentials in separate permissions domains.
5. For the legacy local tunnel, keep the existing tunnel identity and public DNS mapping. Store only its per-tunnel credential JSON and reviewed configuration under `/etc/portfolio-public/tunnel/` (directory root:portfolio-tunnel 0750, files 0640). Set `tunnel` to the existing UUID and `credentials-file` to the JSON's absolute path. After its ACME challenge rule, the apex hostname routes only to `http://127.0.0.1:6050`; the dashboard hostname routes to that same origin so the public app can answer it with the fixed tailnet-only notice instead of leaving an off-tailnet visitor a browser error. The final ingress rule returns `http_status:404`. Review every other hostname, origin, connector replica and Cloudflare private-network route before cutover. The tunnel runtime has no need for the account management certificate or DNS API credentials. Run config validation using this root-provisioned file. If the real deployment is remotely managed, reconcile it with the operator before using this locally managed unit. [Cloudflare tunnel configuration](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/)
6. Copy `sshd_config.example` to root-owned `/etc/ssh/portfolio-deploy.conf` and provision the dedicated Ed25519 host key. Install the restricted CI public key in root-owned `/etc/ssh/portfolio-deploy.keys`, readable by the deploy UID (0640 root:portfolio-deploy). Prefix the key with `restrict,command="/usr/local/libexec/portfolio-public-activate"`. Keep this isolated sshd config independent of other listeners, with no client environment allowlist or user-writable PAM environment. Check `sshd -t -f /etc/ssh/portfolio-deploy.conf` and the effective settings with `sshd -T -f /etc/ssh/portfolio-deploy.conf`. Verify Debian’s root-owned privilege-separation directory `/run/sshd` exists after boot. [Debian sshd configuration](https://manpages.debian.org/bookworm/openssh-server/sshd_config.5.en.html)
7. Install `portfolio-deploy-sshd.socket` and `portfolio-deploy-sshd@.service` as root-owned system units. Substitute the verified Pi Tailscale IPv4 address in the **socket** file. Its Linux listener binds TCP 2222 to that address and to the `tailscale0` device. Each accepted connection runs a separate inetd-mode sshd. Enable the socket after approval and disable the old isolated standalone service if present. Check `ss -lntpe` shows port 2222 on the expected IP and interface, and verify the socket returns after a Tailscale device restart. The separate human SSH route continues on TCP 22. [systemd socket configuration](https://manpages.debian.org/bookworm/systemd/systemd.socket.5.en.html)
8. Limit tailnet ingress to the CI tag on this node’s port 2222. The forced helper checks the actual SSH socket peer using the root-owned local Tailscale daemon and requires both the peer’s node /32 address and `tag:ci` before accepting an archive. Verify `/usr/bin/tailscale` and its standard local socket work for read-only WhoIs under the deploy UID with no operator permissions. Test the approved CI identity, rejection of a reachable ordinary client with a valid test key, and rejection when identity lookup fails. Review tag ownership, CI OAuth trust and overlapping broad grants. [Tailscale WhoIs](https://github.com/tailscale/tailscale/blob/main/cmd/tailscale/cli/whois.go)
9. Configure the shared-Pi packet filter as described in [the dashboard deployment files](../dashboard/). Limit new connections by UID, including LAN, loopback, public internet, IPv4 and IPv6. The deploy helper needs only loopback TCP 6050 for its health check. The tunnel needs that origin, approved DNS and Cloudflare edge transport. The public app needs approved DNS plus its SMTP relay when enabled. Add public-service dependencies discovered during cutover verification to the minimum necessary allowlist. Systemd denies native Tailscale prefixes and excludes AF_UNIX creation for both public daemons. DNS via a remote LAN server or the Tailscale resolver may need an explicit, narrowly scoped alternative. Their inherited journal streams still function. Verify enforcement on this specific kernel; use a working independent firewall even if systemd reports unsupported BPF features. Ensure public UIDs cannot read or traverse private sockets, Caddy/Tailscale keys, admin backups or dashboard configuration. [systemd networking controls](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html) · [systemd sandbox](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)

## Cut over and verify

- Freeze legacy releases. Save root-only, verified backups of current units and drop-ins, both old data locations, the active release reference and tunnel config. Stop the old public writer before the final data copy. Prefer the authoritative `/home/trey/portfolio-deployment/data/submissions.jsonl`; if absent, inspect the legacy `submissions.json` and confirm its line-delimited format. If both the destination and source contain records, reconcile rather than overwriting either file.
- Seed `/var/lib/portfolio-public/` with owner/group `portfolio-public`, directory mode 0700, file mode 0600. Compare source and destination byte counts, SHA-256 and record counts locally without displaying any submissions. Preserve the original. Keep an operator backup on independent storage.
- Following approval, verify units with `systemd-analyze verify`, reload systemd and start the isolated services. Confirm one HTTP writer, listener ownership and the public bind. Validate the public site's existing routes, static assets, public 403, contact persistence/delivery (use approved synthetic mail), and continued restriction of private routes. Test the old deploy key has no authorized access to the new transport or privileged account. Verify the private control socket, tailnet and LAN admin addresses are unreachable by each public daemon/UID. Verify expected positive paths after applying the filter. Perform the kernel/host checks on the Pi with operator approval.
- Set GitHub secret `DEVICE_PUBLIC_SSH_KEY` to the new restricted deploy key; `DEVICE_HOST` to the Pi tailnet IPv4 or a name resolving to it; and `DEVICE_KNOWN_HOSTS` to the **independently verified** line `[DEVICE_HOST]:2222 ssh-ed25519 <public-host-key>` using that same literal hostname or address. Get the key/fingerprint directly from the operator's local console or an established authenticated channel. Isolated mode fails closed if the pinned host entry is missing. Set repository variable `PORTFOLIO_DEPLOY_MODE=isolated` only after the seed release is healthy and pin, listener and grants are verified.
- Revoke the legacy CI SSH key on the host, remove old CI secrets/authorization, broad CI SSH grants, and legacy service-editing sudo rights. Audit unwatched deployment paths and group memberships. Move human recovery access to dedicated named identities. Protect the deployment workflow, branches, Actions dependencies and OIDC/tag minting permissions. A compromised public release can still control public pages, read its SMTP credential and contact data, and interrupt the public service. It shares a kernel and storage hardware with the dashboard.
- Perform one approved workflow dispatch. The isolated path checks the streamed archive digest, serializes updates with flock, rejects unexpected members, requires a prior seed, and atomically switches `current` before a fixed restart and HTTP health check. A failed activation restores the prior symlink, restarts and checks it. A leftover `.rollback-target` triggers restoration on the next attempt. If power or storage failed, inspect release contents, marker and service state before accepting traffic. A fresh run attempt gets a new release ID. The digest checks transport integrity; the restricted SSH identity and repository governance determine who can publish.

## Roll back

For an ordinary public regression, pause CI, take the deployment lock, atomically repoint `current` to the verified preceding release, restart the public service and check `/healthz` plus public routes. Keep the isolated unit, account and persistent data.

For a migration rollback, close private ingress and stop the private dashboard first. Freeze deployment and stop the sole public writer. Back up and verify the **latest** isolated submissions, reconcile records accepted since the cutover into the authoritative legacy location and restore its ownership and permissions before restarting legacy services. Restore the backed-up units/config via a human recovery account. Recheck public origin and contact behavior. Retain the isolated data until reconciliation is verified. Re-enabling the broad legacy deployment identity reopens the original privilege boundary, so keep the private service off that host while legacy deployment is active.
